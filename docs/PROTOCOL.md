# Client–Server Application Protocol (v1 & v2 Specification)

**Owner:** Bùi Hà Yến Vi — Application Protocol & Reliability  
**Scope:** Contract shared by `ChatClient` (Swing TCP), `Chatserver` (TCP `:5000`, UDP `:5001`, HTTP/WS `:8080`), and `webapp` (Next.js Web Client).

---

## 1. Framing and encoding

- Transport: TCP socket (`:5000`), WebSocket JSON-bridge (`:8080/ws`), and UDP datagram socket (`:5001`).
- Framing (TCP): one protocol frame per UTF-8 line (`\n` is the frame delimiter).
- The command name is plain uppercase text.
- User-controlled text fields are Base64-encoded UTF-8. This prevents a `|` or newline in a username/message from changing the frame structure.
- Numeric identifiers and protocol control fields remain plain text.
- Maximum accepted frame size: 65,536 Java characters. Oversized or multi-line frames are rejected.
- Empty fields are preserved by splitting with `split("\\|", -1)`.

## 2. Request format and backward compatibility

Existing commands keep their original field positions. The current client appends an optional request-ID trailer:

```text
COMMAND|field1|field2|...|@RID|<uuid>
```

Examples:

```text
LOGIN|<base64-username>|<base64-password>|@RID|<uuid>
SEND_MESSAGE|<base64-content>|@RID|<uuid>
JOIN_ROOM|12|@RID|<uuid>
```

`JOIN_ROOM` uses a plain integer room ID; its other text fields use Base64. The server reads the fields required by the command and ignores the optional trailer for business logic. A legacy client without `@RID` can still send the original command format, but it cannot correlate application ACKs.

Request IDs are unique per client request and are separate from persisted chat-message IDs. A persisted `NEW_MESSAGE` includes the database message ID generated by the server.

## 3. Application responses

### Successful request

```text
ACK|<uuid>|OK
```

The server sends this only after the request handler completes without reporting an error. For `SEND_MESSAGE`, that means the server's existing save-and-broadcast handler completed; it does **not** mean every recipient displayed or read the message.

### Failed request

```text
ERROR|<base64-human-readable-message>|<uuid-or-empty>|<ERROR_CODE>
```

The human-readable message stays in field 2 so the current Swing UI can display it. The request ID is empty for legacy requests that do not include `@RID`.

Current error codes (`ProtocolErrorCode` v1 + v2):

| Code | Version | Meaning |
|---|---|---|
| `AUTH_FAILED` | v1 | Username/password invalid |
| `AUTH_REQUIRED` | v1 | Login required |
| `ALREADY_AUTHENTICATED` | v1 | This connection already logged in |
| `ALREADY_ONLINE` | v1 | Account has another active connection |
| `USERNAME_TAKEN` | v1 | Username already exists or registration data is invalid |
| `INVALID_ROOM_NAME` | v1 | Room name is blank/invalid |
| `ROOM_NAME_TAKEN` | v1 | Room name already exists |
| `ROOM_NOT_FOUND` | v1 | Requested room does not exist |
| `NOT_IN_ROOM` | v1 | User is not currently in a room |
| `INVALID_RECIPIENT` | v1 | Invalid private-message recipient |
| `USER_OFFLINE` | v1 | Private-message recipient is offline |
| `BAD_REQUEST` | v1 | Invalid field, number, or frame |
| `DATABASE_ERROR` | v1 | Database operation failed |
| `INVALID_STATE` | v1 | Request conflicts with current application state |
| `INTERNAL_ERROR` | v1 | Unexpected server-side failure |
| `PERMISSION_DENIED` | v1 | User lacks permission for this room/friend operation |
| `USER_NOT_FOUND` | v1 | Target user does not exist |

| `INVALID_TOKEN` | v2 | JWT token in `AUTH_TOKEN` or HTTP/WS handshake is malformed, invalid, or expired |

Error codes are for program logic; the encoded message is for people. New errors should use a stable code rather than requiring the client to parse Vietnamese prose.

## 4. Heartbeat and timeout

- Client sends `PING` every 15 seconds.
- Server responds `PONG`.
- Client marks the connection disconnected if no `PONG` arrives for 40 seconds.
- Server socket read timeout is 45 seconds. This lets the server clean up a client whose connection disappears without a clean TCP close.
- TCP keepalive is enabled as an additional OS-level signal; it does not replace the application heartbeat.
- The client uses a 5-second connection-establishment timeout.

The heartbeat checks that the remote application is responsive. It is not a delivery receipt for chat messages.

## 5. Request timeout and retry policy

- Every client command sent through `SocketClient` receives a UUID request ID.
- If an ACK or correlated ERROR does not arrive within 10 seconds, the client emits an internal `REQUEST_TIMEOUT|<uuid>|<command>` event and updates the status area.
- Requests are **not retried automatically**. A timeout does not prove the server failed to execute the request; retrying a non-idempotent command such as `SEND_MESSAGE` could create duplicates.
- If future work adds retry, it must also add server-side deduplication keyed by request ID.

Standalone checks are provided in:

- `ChatClient/test/com/discordmini/client/protocol/ProtocolHandlerTest.java`
- `Chatserver/test/com/discordmini/server/protocol/ProtocolHandlerTest.java`

They cover Unicode/Base64 round-trip, delimiter/newline in payloads, empty fields, request-ID trailers, invalid Base64, multi-line frames, and oversized frames.

Run each test's `main` method from NetBeans or compile it with the matching project's classes. These are protocol unit checks; they do not replace a two-client integration test.

## 7. Manual integration checklist

1. Start PostgreSQL and then the Server; start two Client instances.
2. Register/log in and verify successful commands receive `ACK` and failed commands receive `ERROR` with a stable code.
3. Send a message containing Vietnamese text, emoji, `|`, and multiple lines; verify it arrives as one message and the history remains readable.
4. Stop the server abruptly; verify the client status changes to disconnected after heartbeat timeout, rather than remaining online indefinitely.
5. Leave a client idle while the server is running; verify regular `PING`/`PONG` traffic prevents the 45-second server read timeout.
6. Delay or suppress an ACK in a test environment; verify the client reports request timeout and does not automatically resend the operation.
7. Test malformed and oversized frames against the server; they should be rejected without crashing the whole server process.

## 9. Protocol v2 TCP Extensions

Protocol v2 extends the line-based TCP framing (and mirrors every frame over the WebSocket-to-EventBus bridge) with JWT authentication, Discord-style Guilds & Channels, rich message operations (edit, delete, reactions, pins, read receipts), presence statuses, and WebRTC P2P signaling.

### 9.1 Command & Broadcast Specifications (Protocol v2)

All v2 commands append `|@RID|<uuid>` and receive `ACK|<uuid>|OK` on success or `ERROR|<base64-msg>|<uuid>|<ERROR_CODE>` on failure.

#### 1. `AUTH_TOKEN` — Authenticate Session via JWT
- **Request:**
  ```text
  AUTH_TOKEN|<jwt>|@RID|<uuid>
  ```
- **Response:**
  ```text
  OK|LOGIN|<userId>|<base64-displayName>
  ACK|<uuid>|OK
  ```
- **Error Codes:** `INVALID_TOKEN`, `ALREADY_AUTHENTICATED`, `DATABASE_ERROR`

#### 2. `LIST_GUILDS` — Fetch Joined Guilds & Channels
- **Request:**
  ```text
  LIST_GUILDS|@RID|<uuid>
  ```
- **Response:**
  ```text
  GUILDS|<json-or-pipe-encoded>
  ACK|<uuid>|OK
  ```
  *(Note: `<json-or-pipe-encoded>` is Base64-encoded JSON or pipe/semicolon-delimited guild list so no raw newline or pipe breaks TCP framing).*

#### 3. `CREATE_GUILD` — Create a New Guild (Server)
- **Request:**
  ```text
  CREATE_GUILD|<base64-name>|@RID|<uuid>
  ```
- **Response / Broadcast:**
  ```text
  GUILD_CREATED|<guildId>|<base64-name>|<ownerId>|<inviteCode>
  ACK|<uuid>|OK
  ```
- **Error Codes:** `AUTH_REQUIRED`, `BAD_REQUEST`, `DATABASE_ERROR`

#### 4. `CREATE_CHANNEL` — Create a Channel Inside a Guild
- **Request:**
  ```text
  CREATE_CHANNEL|<guildId>|<base64-name>|<type:text|voice>|@RID|<uuid>
  ```
- **Response / Broadcast:**
  ```text
  CHANNEL_CREATED|<guildId>|<roomId>|<base64-name>|<type:text|voice>
  ACK|<uuid>|OK
  ```
- **Error Codes:** `AUTH_REQUIRED`, `GUILD_NOT_FOUND`, `FORBIDDEN`, `INVALID_ROOM_NAME`, `ROOM_NAME_TAKEN`

#### 5. `EDIT_MSG` — Edit an Existing Message
- **Request:**
  ```text
  EDIT_MSG|<messageId>|<base64-newContent>|@RID|<uuid>
  ```
- **Broadcast to Room:**
  ```text
  MSG_EDITED|<roomId>|<messageId>|<base64-newContent>|<editedAt>
  ```
- **Sender Response:** `ACK|<uuid>|OK`
- **Error Codes:** `MESSAGE_NOT_FOUND`, `FORBIDDEN`, `BAD_REQUEST`

#### 6. `DELETE_MSG` — Soft-Delete a Message
- **Request:**
  ```text
  DELETE_MSG|<messageId>|@RID|<uuid>
  ```
- **Broadcast to Room:**
  ```text
  MSG_DELETED|<roomId>|<messageId>
  ```
- **Sender Response:** `ACK|<uuid>|OK`
- **Error Codes:** `MESSAGE_NOT_FOUND`, `FORBIDDEN`

#### 7. `REACT_MSG` — Toggle Emoji Reaction on a Message
- **Request:**
  ```text
  REACT_MSG|<messageId>|<base64-emoji>|@RID|<uuid>
  ```
- **Broadcast to Room:**
  ```text
  MSG_REACTED|<roomId>|<messageId>|<userId>|<base64-emoji>|<added:1|0>
  ```
- **Sender Response:** `ACK|<uuid>|OK`
- **Error Codes:** `MESSAGE_NOT_FOUND`, `BAD_REQUEST`

#### 8. `PIN_MSG` — Pin or Unpin a Message in a Room
- **Request:**
  ```text
  PIN_MSG|<messageId>|<pinned:1|0>|@RID|<uuid>
  ```
- **Broadcast to Room:**
  ```text
  MSG_PINNED|<roomId>|<messageId>|<pinned:1|0>
  ```
- **Sender Response:** `ACK|<uuid>|OK`
- **Error Codes:** `MESSAGE_NOT_FOUND`, `FORBIDDEN`

#### 9. `MARK_READ` — Update Read Receipt Cursor for a Room
- **Request:**
  ```text
  MARK_READ|<roomId>|<lastMessageId>|@RID|<uuid>
  ```
- **Response / Broadcast:**
  ```text
  READ_UPDATED|<roomId>|<userId>|<lastMessageId>
  ACK|<uuid>|OK
  ```
- **Error Codes:** `CHANNEL_NOT_FOUND`, `BAD_REQUEST`

#### 10. `PRESENCE` — Update User Presence Status
- **Request:**
  ```text
  PRESENCE|<status:ONLINE|IDLE|DND|OFFLINE>|@RID|<uuid>
  ```
- **Global Broadcast:**
  ```text
  PRESENCE_UPDATED|<userId>|<status:ONLINE|IDLE|DND|OFFLINE>
  ```
- **Sender Response:** `ACK|<uuid>|OK`
- **Error Codes:** `BAD_REQUEST`

#### 11. `SIGNAL_OFFER` — WebRTC P2P SDP Offer Relay
- **Request:**
  ```text
  SIGNAL_OFFER|<roomId>|<targetUserId>|<base64-sdp>|@RID|<uuid>
  ```

#### 12. `SIGNAL_ANSWER` — WebRTC P2P SDP Answer Relay

#### 13. `SIGNAL_ICE` — WebRTC P2P ICE Candidate Relay

## 10. UDP Protocol (`:5001` `DatagramSocket`)

To demonstrate low-overhead, connectionless transport alongside reliable TCP/WebSocket streams, `Chatserver` binds a `java.net.DatagramSocket` on port `:5001` (`UDP_PORT`, default `5001`) for ephemeral real-time signals where occasional packet loss is acceptable and head-of-line blocking is undesirable.

### 10.1 Datagram Framing Rules
- Encoding: UTF-8 single-line text without trailing newline required (trimmed on receipt).
- Maximum datagram payload: **1,024 bytes** (`byte[1024]`). Datagrams larger than 1,024 bytes are truncated or dropped silently.
- Delimiter: `|` (pipe character). User display names are Base64-encoded UTF-8.

### 10.2 UDP Datagram Types

#### 1. `UDP_PING` / `UDP_PONG` — Sub-millisecond RTT Probe
- **Client → Server (`:5001`):**
  ```text
  UDP_PING|<seq>|<clientTimestampMs>|<userId>
  ```
- **Server → Client (Immediate UDP reply to sender `SocketAddress`):**
  ```text
  UDP_PONG|<seq>|<clientTimestampMs>|<serverTimestampMs>
  ```
  - `<seq>`: monotonically increasing integer sequence number per client session.
  - `<clientTimestampMs>`: client epoch timestamp in milliseconds when `UDP_PING` was transmitted.
  - `<serverTimestampMs>`: server epoch timestamp (`System.currentTimeMillis()`) when `UDP_PING` was processed.
  - Side effect: Server records the incoming and outgoing UDP frames via `EventBus.recordProtocolFrame(...)` so the Network Monitor Drawer can inspect live UDP traffic and calculate jitter/packet loss.

#### 2. `UDP_TYPING` — Ephemeral Typing Indicator
- **Client → Server (`:5001`):**
  ```text
  UDP_TYPING|<userId>|<roomId>|<isTyping:1|0>|<base64-displayName>
  ```
- **Server Action:**
  - Publishes `TYPING_UPDATE` to all members in `<roomId>` (excluding `<userId>`) via `EventBus.publishToRoom(...)`:
    - TCP frame: `TYPING_UPDATE|<roomId>|<userId>|<isTyping:1|0>|<base64-displayName>`
    - WS event type: `"TYPING_UPDATE"`

#### 3. `UDP_PRESENCE` — Lightweight Presence & Heartbeat Beacon
- **Client → Server (`:5001`):**
  ```text
  UDP_PRESENCE|<userId>|<status:ONLINE|IDLE|DND|OFFLINE>
  ```
- **Server Action:**
  - Updates user's last-seen heartbeat timestamp and broadcasts presence state changes via `EventBus.publishGlobal(...)`:
    - TCP frame: `PRESENCE_UPDATED|<userId>|<status>`
    - WS event type: `"PRESENCE_UPDATED"`

### 10.3 UDP Fallback Rule (Cloud / Restricted Firewall Mode)
Browser sandboxes and single-port cloud reverse proxies (e.g., Render/Railway exposing only HTTP/WS `:8080`) cannot send raw UDP packets directly to `:5001` unless proxied through a local Node.js API route or running on LAN/localhost.
- **Fallback Mechanism:** When UDP `:5001` is unreachable, blocked, or running in Single-Port cloud mode, the client automatically sends `PING_RTT` / `TYPING_START` / `PRESENCE_UPDATE` over the active WebSocket/TCP connection.
- **UI Indicator Requirement:** When operating in fallback mode, the Network Monitor Drawer **must** display the badge `"UDP fallback active"` so evaluators can clearly distinguish direct UDP `:5001` datagrams from WS/TCP fallback frames.

### 11.2 Package `com.discordmini.server.auth`

#### `JwtUtil.java`
```java
package com.discordmini.server.auth;

public class JwtUtil {
    public record JwtClaims(int userId, String username, String displayName, long exp) {}

    public static String generateToken(int userId, String username, String displayName);
    public static JwtClaims verifyToken(String token);
}
```
- **Implementation Notes for `JwtUtil`:**
  - Uses pure JDK `javax.crypto.Mac` (`HmacSHA256`) + `java.util.Base64.getUrlEncoder().withoutPadding()` so zero external JWT dependencies are required.
  - Reads secret key from environment variable `JWT_SECRET` with a safe development fallback secret.
  - `verifyToken(String token)` returns `JwtClaims` if valid and unexpired, or throws `IllegalArgumentException` / returns `null` when invalid or expired (callers translate this into `ProtocolErrorCode.INVALID_TOKEN`).
